Telemetry is cheap. Fan-out is not.

A layer-by-layer benchmark of the irDashies native SDK read, projection, Electron IPC, renderer store delivery, widget computation, and Chromium rendering path using one deterministic 10-minute iRacing replay.

The short answer

No single “telemetry store” or native call explains the whole profile. The evidence splits cleanly: IPC/store delivery creates a measurable empty-dashboard floor, while subscribed widget work and Chromium rendering dominate the full dashboard.

01

The SDK is not the primary bottleneck

A normal allowlisted tick averages about 0.75 ms end to end in the main-process telemetry function. Native telemetry read is the largest part at roughly 0.58–0.62 ms, but the full app consumes far more CPU after the message leaves that function.

02

Delivery leaks before widgets render

Turning on allowlisted delivery for three empty windows adds 0.54 percentage points of app CPU and 10.75 MB/min of working-set growth. That isolates a real IPC, deserialization, or store-snapshot retention cost without widget computation.

03

Widgets and paint own the full cost

Enabling the normal 18-widget dashboard adds another 7.80 percentage points of CPU and 40.63 MB/min of working-set growth. The synchronous store callback remains only about 0.4 ms at p99, placing most of the extra work downstream in derived state, React updates, layout, and paint.

Recommended sequence

Change the fan-out contract before investing in a native rewrite. Each recommendation maps to the existing architecture phases and preserves the current allowlist safety net.

P0

Protect the telemetry allowlist

Derive or validate it against declared consumers in CI. Raw payloads doubled broadcast latency and nearly doubled callback p99, while producing extreme allocation growth.

Prevents a measured 2–4× regression
P1

Replace snapshot broadcast with per-window channels

Subscribe each renderer only to the keys and rates required by its mounted widgets. Keep smooth inputs at full rate; bucket position and display telemetry to their actual precision and refresh needs.

Architecture Phase 3
P1

Heap-profile the empty delivery boundary

Compare allocation stacks with delivery off and on. Inspect Electron structured-clone objects, TelemetryStore snapshot replacement, and retained selector results. Do not mutate the store snapshot in place merely to reduce allocations.

Targets +10.75 MB/min before widgets
P2

Confirm Input, Flag, Weather, Blind Spot, and Fuel

These five widgets produced the strongest positive active-renderer allocation slopes. Run longer confirmation captures, beginning with Input at +33.51 MB/min, using V8 allocation sampling and React profiling to identify retained owners.

Highest short-run allocation signals
P2

Remove the per-tick session-data fetch

Parsed YAML is already cached by data version, but the bridge still calls getSessionData() on every processed tick. Check a lightweight version first, or expose one from the addon if required, and fetch the session string only when it changes. Move parsing to a worker only if a live trace later connects refresh spikes to visible stalls.

Removes tail latency, not dominant CPU
P3

Defer native and worker-thread rewrites

The native read is the largest measured main-function section, but it is still below one millisecond on average. The controlled deltas show much larger costs in fan-out, renderer computation, and Chromium.

Revisit only after Phase 3 evidence

Limitations

  • Windows Application Control blocked the packaged executable, so all comparative overlay runs use the same Electron development target. Absolute production memory may differ; within-target A/B deltas remain valid.
  • FPS, CPU, and GPU fields inside the iRacing tape are historical values from the recorded session and are not used to evaluate the current host.
  • Five-minute captures establish direction but do not replace a multi-hour live race, package build, V8 heap snapshot, or ETW trace.
  • A stable 60 Hz renderer in this replay means the reported long-session stutter was not reproduced. Memory growth is a risk signal, not proof of the exact user-visible pause mechanism.
